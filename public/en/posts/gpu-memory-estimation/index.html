Estimating GPU Memory: How Much VRAM a Model Needs From Its Parameter Count

Before putting a model on a GPU, I want to know two things first: does it fit, and how many requests can it hold at once. The goal of this post is to stop finding out by launching the server and waiting for an OOM.

2026.11.188 min vLLMKV CacheQuantization

GPU memory splits into four parts

When you serve an LLM, model weights are not the only thing taking up GPU memory. Splitting it into four parts makes the math simple.

Weights

The model parameters themselves. Once the model and precision are chosen, their size is fixed.

KV Cache

Space that stores the Key and Value of every token processed so far, per request. It grows with token count and the number of concurrent requests.

Activations

Intermediate results used briefly during one forward pass. The peak depends on how many tokens are processed at once.

Runtime overhead

The CUDA context, cuBLAS workspace, CUDA Graph capture and so on. A roughly fixed amount per GPU, regardless of the model.

GB and GiB are not the same

1 GiB = 1024³ bytes and 1 GB = 1000³ bytes, about 7% apart. An 8B model's BF16 weights are 16.1 GB but 15.0 GiB. nvidia-smi reports MiB and vLLM logs report GiB, so this post uses GiB throughout.

The INT4 numbers are theoretical. Real quantized models keep the embeddings and lm_head in BF16 and add a scale value per group, so they are larger. It is safer to budget about 37 GiB for a 70B INT4 model.

KV cache: the variable that sets concurrency

When a Transformer generates a new token, it looks again at the Key and Value of every previous token. The KV cache stores them so they are not recomputed every step. The size per token is set by the model architecture.

KV per token = 2 × layers × KV heads × head_dim × bytesThe 2 is for K and V. Total KV = KV per token × tokens × concurrent requests.

Llama 3.1 8B328128128 KiB
Llama 3.1 70B808128320 KiB

320 KiB looks small, but it multiplies quickly. If 16 requests of 8K tokens hit a 70B model at the same time, that is 320 KiB × 8,192 × 16 = 40 GiB, on top of the weights.

A common mistake

Using num_attention_heads (64 for 70B) as the KV head count gives a result 8 times too large. Recent models cut down KV heads with GQA (Grouped Query Attention), so always read num_key_value_heads.

Activations and overhead: start with a rule of thumb, then measure

Activations depend on the number of tokens processed per step (vLLM's max_num_batched_tokens) and the hidden size, and overhead depends on the driver and CUDA Graph settings. No single formula covers them cleanly.

So at the planning stage I set aside 1 to 3 GiB per GPU, then launch the model, check the vLLM logs and nvidia-smi, and replace it with the value from my own environment. At startup, vLLM runs a dummy input to measure the activation peak and gives the remaining space to the KV cache.

Putting it together for vLLM

KV space = GPU memory × gpu-memory-utilization − weights − activations and overheadThis value ÷ KV per token = total tokens the server can hold at once.

An 8B model on one 24 GiB GPU

  • Budget: 24 × 0.9 = 21.6 GiB
  • Subtract 15.0 GiB of weights and 2 GiB of activations and overhead, leaving 4.6 GiB for KV
  • 4.6 GiB ÷ 128 KiB = about 38,000 tokens. With 4K-token requests, that is about 9 at once.

This table is the first piece of evidence for "why does a 70B model OOM" and "which quantization did we pick, and why". If it has to fit on one GPU, INT4 leaves the most KV space. If quality loss is a concern, add GPUs and stay on BF16. The point is to be able to explain this trade-off in numbers.

Where to check in a real environment

config.json

In the Hugging Face model repo, read num_hidden_layers, num_key_value_heads and hidden_size / num_attention_heads (= head_dim).

vLLM startup log

Shows the memory taken by the model weights, the size reserved for the KV cache and the maximum concurrency. Record these next to your calculated values.

nvidia-smi

Shows real usage per process. vLLM reserves its whole budget up front, so it is normal for the GPU to look almost full even with no requests.

# Minimal record to keep calculated and measured values side by side
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --gpu-memory-utilization 0.9 \
  --max-model-len 8192 2>&1 | tee serve.log

nvidia-smi --query-gpu=memory.used,memory.total --format=csv

Summary

  • Look at GPU memory as four parts: weights, KV cache, activations and overhead.
  • Weights = parameter count × bytes. Halve the precision and the weights halve too.
  • KV per token = 2 × layers × KV heads × head_dim × bytes. For KV heads, use num_key_value_heads.
  • Smaller weights leave more space for the KV cache, which raises concurrency.
  • Budget 1 to 3 GiB per GPU for activations and overhead, then measure to find your environment's value.
